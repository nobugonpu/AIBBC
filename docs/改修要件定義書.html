Lu-177治療患者スケジューラ 改修要件定義書

文書番号：〔　　　〕／版：0.1（案）／作成日：〔　年　月　日〕
提出先：医療情報管理運営委員会　御中／申請部署：RI室（核医学）／作成：新留 信幸／責任者：〔氏名〕・副責任者：〔氏名〕
本書の目的
現行の「Lu-177治療患者スケジューラ」を、医療情報部のご指摘（共通パスワード・利用者名手入力・可用性/保守性 等）を踏まえて設計から見直し・改修するにあたり、その改修要件を定義し、委員会でのご審議・ご承認をお願いするものです。承認後、現場検証を経て暫定運用へ移行する前提です。

1背景と経緯

  • 目的：ルタテラ・プルヴィクト（Lu-177）治療の予約は、治療間隔・病室重複・祝日週・薬剤発注締切など制約が多く、手作業では見落としが生じやすい。予約ミスは治療遅延・薬剤ロスに直結するため、ヒューマンエラー低減＝患者安全の向上を目的とする。
  • 医療情報部からのご指摘：①共通パスワードは不可 ②利用者名の手入力は不可 ③独自ツールは原則不可であり、可用性・保守性・他システムへの影響・セキュリティを考慮のうえ、設計見直し・委員会承認・現場検証が必要。
  • 代替手段の検討結果：暫定策としてExcel版・Access版を試作したが、スケジューリング判定が複雑で関数・クエリだけでは安定自動化できず、手作業補正が多く実運用に耐えないと判断。ポータル共有フォルダへの設置は断念。
  • 方針転換：院内ポータルへの設置は行わず、既存のデスクトップアプリを、RI室が使用する指定端末（ネット端末）に設置して運用する形態を採用する。アプリは外部・院内網へ一切通信しないため、ネット端末に設置しても患者データが外部へ出ることはない。

2対象システムと運用形態

対象Lu-177治療患者スケジューラ（治療予定の作成・管理・印刷）
形態ローカル完結型のデスクトップアプリ（Windows x64）。RI室が使用する指定端末（ネット端末）に設置。ユーザー単位でインストール（管理者権限不要）。
通信外部・院内網ともに一切通信しない（完全オフライン）。
データ共有当面は「親機1台方式」（入力・保存は指定1台のみ、他メンバーは印刷物で共有）。同時共有は正式システム調達までの将来課題。
データ保存指定端末内に暗号化して保存。定期的に書き出しファイルでバックアップ。

3機能要件（改修項目）

#項目現状改修後（要件）区分
F1個人認証全員共通の1パスワード利用者ごとの個人アカウント（ID＋各自パスワード）で認証。共通パスワードを廃止。必須
F2利用者の記録氏名を手入力手入力を廃止し、ログイン中の利用者を自動で記録。必須
F3権限管理管理者PWで一部制限役割（管理者／一般）を導入し、機能ごとに権限制御。必須
F4パスワード運用桁数チェックのみ有効桁数・連続失敗時ロック・変更手順を規定。推奨
F5操作履歴（監査ログ）実装済（氏名手入力基準）個人アカウントに紐付けて改ざん不可（追記のみ）で記録。CSV出力。必須
F6スケジューリング実装済治療間隔厳守・重複回避・祝日週除外・発注締切判定・全サイクル登録・延期調整を維持。維持
F7データ入出力DB保存暗号化した書き出し／読み込み（バックアップ・受け渡し）に対応。推奨
F8印刷実装済患者用予定表・スタッフ用一覧の印刷を維持。維持
認証と暗号化の両立（F1の技術方針）
データ本体は1本の鍵で暗号化し、その鍵を利用者ごとに各自のパスワードで包んで保管（エンベロープ暗号化）する。これにより共通パスワードを廃止しつつ、同一データを複数利用者が各自の認証で開ける。利用者の追加・削除は「包み」の追加・削除で行う。

4非機能要件

観点要件
セキュリティ院外・院内網へ通信しない／保存データはAES-256で暗号化／患者情報は患者ID中心（氏名保有を最小化）／ソースはレビュー可能。
可用性指定端末で起動が単純。定期バックアップ（書き出しファイル）で消失に備える。
保守性インストーラの差し替えで更新（ユーザー単位）。手順書・ソース公開・二名体制で属人化を排除。
他システムへの影響スタンドアロン・通信なしのため他システムへ影響を与えない。
性能数十名規模の予定管理を想定。端末内処理で十分な応答性。

5取り扱うデータ項目

患者ID・治療種別（薬剤）・治療日/入院日/退院日・サイクル番号・ステータス・発注締切・メモ。患者氏名は任意とし、原則は患者IDで管理（個人情報の保有を最小化）。

6スコープ外（将来課題）

  • 複数端末でのリアルタイム同時共有（＝情報部管理サーバー／正式システムの領域）。
  • 院内認証基盤（Active Directory 等）との連携（SSO）。
  • 他部門システムとのデータ連携。

7体制・責任

  • 管理主体：RI室（核医学）。責任者〔氏名〕・副責任者〔氏名〕の二名体制。
  • 資産の帰属：ソース一式を院の資産として管理（特定個人の所有物にしない）。
  • 運用規程：利用者・利用目的・データ取扱い・バックアップ・保守手順を規程化し、情報部の管理下に置く。

8導入・検証ステップ

  1. 本要件定義の承認（委員会）。
  2. 設計・改修（F1〜F5 を中心に実装）。セキュリティ設計書を作成。
  3. 情報部によるソースレビュー・セキュリティ確認、運用端末・保存場所の決定。
  4. 現場検証（少人数・親機1台方式）→ 問題なければ暫定運用へ。

9リスクと対策

リスク影響対策
患者情報の漏洩大通信なし＋暗号化＋患者ID中心＋保存場所を情報部管理下に
データ消失（端末故障等）中定期バックアップ（書き出しファイル）
担当者不在による停止中手順書＋ソース公開＋二名体制＋データ可搬性
不正操作・変更中個人認証＋改ざん不可の操作履歴（F1・F5）
同時編集による不整合中親機1台方式（入力を1台に限定）
